# 日常完整流程验收

## 本轮结论 · 2026-10-22

以临时数据库验证采购→核对入库→推荐食谱→烹饪→核对并确认消耗→再次补货，包含页面刷新、Core重启和请求重放。全过程不依赖开发板联网。

本轮同时修复了流程中复现的两个问题：再次打开同一道菜会重建会话、丢失步骤；反复计算缺货会重复加入已买待确认的物品。食谱清单复核还会移除已由库存补齐的旧待购计划项，保留手动和已购记录。

## 可以怎样试用

1. 在“今日”或“今晚吃什么”选番茄炒蛋，点“缺少食材加入清单”。这是采购计划，不增加库存。
2. 在购物清单逐项勾选已买到，核对实际数量、位置和日期，明确确认入库。也可从“待确认”继续。
3. 回到菜谱，食材已齐。点“开始做饭”，试用下一步、上一步、再说一遍或问用量。
4. 离开页面、刷新或重启Core后，首页显示“上次的菜，接着做”；再次打开同一道菜、同人数会继续原步骤，不创建新会话。已经进入用量确认时，首页保留继续核对入口。
5. 网页选择另一道菜或改人数时先显示换菜确认。取消保留原进度；确认后才替换，且带原任务ID和版本防止覆盖后续进度。替换不扣原任务库存。
6. 点“做完了”只生成按批次的用量确认清单。实际用量不同，选“不扣减”后到库存逐批记录；核对无误再点“确认扣减”。
7. 完成后按当前库存再次加入缺货，生成新一轮待购项。原入库采购记录保留，不把旧批次重新入库。

同一道菜已经结束后再开始，会创建新会话；不同菜或不同人数仍是一次新的做饭任务。当前只支持一个烹饪会话。网页增加了换菜确认，旧API以及明确说出“开始做另一道菜”的语音行为保留兼容替换逻辑，不能将网页确认称为所有客户端均已改造。

## 食谱购物计划复核

重复加入同菜、同人数缺货时，会按当前可用库存同步该食谱尚未购买的计划数量。已经齐备的计划项会移除；手动购物项、其他菜的计划、已买与已入库记录保留。如果某项已买但尚未确认入库，提示先去待确认处理，不再为该项重复生成待购记录，也不把计划数量当实际库存。

如已由其他方式录入库存，但旧食谱计划仍在清单里，可回到对应菜谱点“复核购物清单”。当前仍依赖能在推荐或目录中找到这道菜；旧生成菜谱被替换后不自动推断新计划，可手动移除对应旧项。不同食谱计划不自动合并为一顿饭的采购总量。

## CLI验收

新增`tests/daily-workflow.test.ts`两组集成测试，全量测试共52项：

- 空库生成2项采购，分别确认入库，重放不重复新增；菜谱显示主要食材已齐。
- 做饭第2步重启Core，重放“下一步”不多前进一步；再次开始同菜继续原会话。
- 完成后进入用量待确认，库存仍保持原值；再重启后继续用量确认，显式扣减与重复请求仅产生一次消耗。
- 过时换菜版本被拒绝。
- 再次生成2项补货，多次复核不累加，按实际数量各多买1个确认新批次；最终4批、6条事件，旧批次归零保留。
- 最终数据可导出并通过新备份校验。
- 复核清除已齐的旧食谱待购项，保留手动项和已买记录；复核写入中途失败整笔回滚。

## 浏览器验收

从空库真实操作番茄2个、鸡蛋3个采购入库；第2步离开、再次打开以及整页刷新均可续做。尝试换番茄蛋花汤会出现确认面板，取消后仍保留番茄炒蛋第2步。问用量得到本地规则回答；做完但未确认时仍是2批库存、2条入库事件。

明确确认后两批数量归零，事件变为4条；再次生成番茄2个、鸡蛋3个的补货项，页面同时显示旧入库记录和新待购记录。浏览器停在该补货阶段，CLI额外验证了再次入库。证据见`product-evidence/daily-workflow-20261022.json`。
