# 家庭时区与日期

更新：2026-10-23。

## 使用方式

进入“设置 → 家庭时区与日期”，选择北京/上海等常用时区，或输入其他有效 IANA 名称，再点“保存家庭时区”。页面显示 Core 计算的“家庭今天”。旧数据和未配置的新家庭保持 UTC，程序不会根据电脑或浏览器时区自动修改设置。

保存后，首页优先食用、库存临期、食谱可用食材、烹饪确认用量、文字语音解析、设备屏幕投影和 Web 默认日期都使用家庭日期。开封提醒按日历天计算，跨夏令时不使用本地固定24小时推算。Web 的事件、图片记录、设备通信和备份记录时间按家庭时区显示。

时区设置不会改写库存中已有的购买、包装、建议或开封日期，也不会自动扣减库存。原先录错的日期仍需手动纠正。购买/开封等日期是无时区的日历日期；事件时间仍保存为 UTC ISO 时间戳，两者不能混用。

## 一致性与恢复

- Core 在一次状态响应中捕获一个家庭日期，首页和食谱不会在跨午夜时各用一天。设备投影共用同一规则，未改变设备协议或重刷固件。
- 设置带版本号，过时页面不能静默覆盖更新。写请求沿用登录、来源保护、事务和幂等回执。
- 异步写请求若在等待模型或排队期间跨过家庭午夜，或家庭时区发生变化，提交前拒绝并要求重新确认；已完成请求跨日重放仍返回原结果，避免重复入库。
- 烹饪待确认用量在实际扣减时重新检查有效日期；跨午夜过期的批次不会继续扣减。
- 设置保存在 SQLite 的现有 app_state 中，无需修改历史 migration。备份包含家庭时区并验证有效值；旧备份无此设置时恢复为 UTC。导出文件名使用家庭日期。
- Web 每3秒获取状态；已打开且由用户编辑的日期字段不会被后台刷新自动覆盖。切换家庭时区后应重新核对尚未提交的表单。模型调用和离线设备仍依赖正常网络与同步。

## 本轮验证

使用临时时钟验证上海午夜、洛杉矶夏令时、跨年、闰日、跨日请求拦截、幂等重放、备份与旧格式兼容、鉴权及烹饪过期拒绝。Chrome 手机模拟验证320/390像素设置页、保存与刷新、无效输入、默认购买日期和库存不变；原74项手机基线复测通过。

未修改日常库存或家庭时区，未调用真实模型、未操作开发板，真实手机按用户要求跳过。详情见[结构化证据](product-evidence/household-calendar-20261023.json)。
