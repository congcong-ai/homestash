# FreshMate 配置与 OTA

更新：2026-10-20。板卡为 ESP32-S31-Korvo-1 V1.1。本文区分功能实现、自动测试与实际板卡验证。

## 日常使用

1. 在项目根目录运行 `pnpm dev`，Web 为 `http://127.0.0.1:3000/app`。管理 API 仅本机3100，设备 API 使用3101；电脑和设备需在可互通网络。
2. LCD 右上角“设置 → 网络”可扫描网络、选择 SSID、输入密码并连接，也可恢复自动选择。拿到 IP 后才保存；错误密码不覆盖此前成功配置。企业网络仅支持提前注入账号和证书的配置。
3. “设置 → Core”填写电脑的局域网地址（如 `http://电脑IP:3101`）、设备 ID 和设备凭据。必须与 Core `.env` 一致。凭据输入框不显示原值，留空保留已有值；首次必须填写。设备不接收百炼 API Key。
4. 根目录执行 `pnpm hardware:build:generic`，应用位于 `firmware/freshmate-korvo/build/homestash_freshmate.bin`。此方式不读取 `data/hardware/device.env`，不嵌入个人网络/设备凭据。构建前请设置正式版本，构建脚本会重新配置 CMake，避免环境变量变化沿用旧版本。
5. Web“冰箱贴 → 设备连接与更新”选择应用 `.bin` 发布。不要选择 bootloader、分区表、整片备份，或包含个人配置的调试固件。发布不会自动重启设备。
6. LCD“设置 → 更新 → 检查更新”，核对版本，点击安装，再次确认。下载期间保持供电，成功后自动重启。录音/业务处理期间不能升级。

通用固件保留已有 NVS 的网络和 Core 配置；空白新设备需先在 LCD 配置。升级界面不会给 Web 返回网络密码或设备 Token。

## 首次安装与恢复

旧分区只有 factory，需要先使用 UART 安装新增分区的基础固件。保留 NVS/PHY/factory，增加 OTADATA、ota_0 和 ota_1 两个4 MiB槽。首次刷写和 UART 恢复会初始化 OTA 选择区并启动 factory，不擦 NVS 或格式化 SD。

使用 `scripts/hardware/flash.py` 时必须指定原板备份 `--backup`，以及当前整片核验备份 `--migration-backup`；脚本先核对文件摘要、16 MiB长度、USB序列号、设备 MAC 和每段写入范围，再执行烧录。`--build-dir` 可使用已冻结的镜像目录，避免后台构建更换待写文件。

本轮迁移前恢复资产位于本机忽略目录 `data/hardware/pre-ota-20261020/`。完整镜像由当前头64 KiB、已核验应用和原始整片备份重建，再对设备整个16 MiB执行 `verify-flash`，摘要一致。该文件含设备私密配置，不得发布或提交。实际整片写回恢复未执行。

正常 OTA 写非运行槽，只有长度、SHA-256、SDK 镜像及应用描述校验通过才切换启动。未完成下载不会替换当前启动槽。启用 SDK 启动回滚；新应用完成基础初始化并运行30秒后才标记有效，SD初始化失败请求回滚。故障启动自动回滚、升级中物理断电仍需专项真机验证，不能从普通升级成功推导。

## 协议和安全边界

- 管理入口：`GET /api/firmware`、`POST /api/firmware`（二进制应用，最大4 MiB）。Web沿用管理接口认证和同源限制。
- 设备入口：`GET /device/v1/firmware`、`GET /device/v1/firmware/:sha256`。必须同时通过设备 ID / Bearer Token 校验，拒绝浏览器 Origin。
- Core校验板型、应用名、版本、ESP分段校验和与附加SHA-256；私有文件和发布状态保存在本机，重启仍保留。没有修改历史数据库 migration。
- manifest 使用设备Token作 HMAC-SHA256，绑定摘要、长度、版本、项目和芯片。安装前再次检查配置revision与已确认摘要，变化则要求重查。
- HMAC不是硬件安全启动签名；HTTP不加密。当前是可信局域网PoC，公网分发、独立签名密钥、Secure Boot/防降级及生产密钥轮换仍未实现。
- OTA不修改库存。图片只产生候选，仍需网页明确确认才入库。

## 验收结果

真实OTA已从factory的0.3.1升级至ota_0的0.3.2，启动自检通过、认证心跳ESP_OK。通用镜像2,189,680字节，SHA-256为 `0552da76cc28f0b4550e93ba04279e83cef5d8ce92f765c7943e8f7202bee205`；不含本机配置，升级后Wi-Fi/Core均从NVS恢复。SDK上报的短ELF摘要与发布应用描述前缀一致。故意在32 KiB截断下载时设备拒绝不完整镜像，仍运行原应用；此后恢复正常Core并完成正式升级。OTA前后各一次相机抓图与上传成功，均0个候选，库存及事件完整数据保持4项/4条不变。

32项软件测试、lint、typecheck、Web构建、固件构建和直接编译Wi-Fi管理C代码的主机检查通过。最终结果和固件摘要见 `hardware-evidence/maintenance-20261020.json`。用户已实际确认“设置”和 Wi-Fi 列表正常；串口 Core 保存与手动 Wi-Fi 连接均返回成功，获得IP后心跳正常。修复了新增配置命令在原3 KiB串口任务栈上触发的溢出，增加至12 KiB，重新烧录验证。

2026-10-20集中验收中，用户已确认LCD密码键盘输入、连接、Core保持原值且凭据留空保存、返回首页全部成功。LCD二次确认升级的完整触摸操作仍需单独验证；串口升级不会冒充这些触摸动作。BLE诊断通过也不表示已经实现BLE配网。长时间运行、复杂网络切换、功耗与最终续航不在本轮结论内。

0.3.3增加受控3秒定时休眠实验、Idle/Active/Light Sleep/Deep Sleep状态、内部堆内存和OTA确认状态上报，以及Core连续连接失败时至少间隔120秒的Wi-Fi恢复尝试。没有实现自动休眠或SET深睡唤醒，不把实验入口称为最终低功耗方案。完整结果见 [Phase 1验收](PHASE_1_ACCEPTANCE.md)。

0.3.5为集中验收的当前固件。使用现有LVGL适配器保留UI对象并在睡前释放RGB panel/DMA，醒来重新建面板和恢复显示；Light/Deep Sleep真实定时唤醒通过。0.3.3/0.3.4失败记录仍保留，不能将其作为稳定发布版。

## 更新中断后为什么显示首页

更新页属于临时交互，不保存在NVS；每次重新上电都会先回到首页。未完成的下载不会自动续传，也不会仅因为回到首页就算更新失败。应核对实际固件版本、运行分区、OTA有效状态、联网和业务是否恢复；重新更新需再次检查并确认安装。只有镜像完整校验后才切换启动槽，因此下载完成后断电与写入中途断电需要分别记录。

用户后续已确认唤醒后LCD首页、“家里有什么”真实录音及播报均正常。另一次用户报告下载提示后断电、约3秒后重连；实测运行0.3.5/ota_0/valid（此前为ota_1），说明至少已切换启动槽。该次更新可能已完成才断电，不能单凭界面提示当成“写到一半断电”证据；受控重复窗口未发生新物理断电，随后停止服务验证下载中断，保留原槽；从正常Core完整重试后已运行0.3.5/ota_1/valid，首页和心跳恢复。精确写入中途物理断电保留为专项未覆盖，不再将其误报为已通过。

### 后续受控中途断电复测

用户重新执行全部断电约3秒后接回UART。本次慢速传输在262,144 / 2,216,720字节中断，下载期间UART断开，Core随后重新收到启动后心跳；仍运行原ota_1 / 0.3.5 / valid，首页及联网恢复。此项取得了下载中途断电保留原应用的证据，取代此前“该阶段未覆盖”的结论；不代表覆盖Flash全部指令及启动元数据提交瞬间的故障时序。

收尾已完成：用户通过LCD恢复正常Core（3101）并确认安装，自动重启回首页。最终实测0.3.5 / ota_0 / valid；关闭3102临时代理后仍收到新心跳，确认直连正常Core恢复。库存仍为4项、4条事件。临时代理及串口监控已停止，私密命令队列已清空，无需继续拔电。
