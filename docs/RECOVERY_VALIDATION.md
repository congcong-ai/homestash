# 断网重试与录音恢复验收

日期：2026-10-18。

## 修复的问题

第一版使用 `pending.id` 和 `pending.wav` 两个文件配对，录音中断没有恢复逻辑；ID 和 WAV 更新之间的中断也可能留下孤立文件。恢复版把请求 UUID 编入文件名，上传前不再依赖另一个文件写入成功。

## 文件状态

全部只在 `/sdcard/homestash/outbox/` 下操作：

- `<uuid>.part`：正在录音。先写固定 WAV 头；约每 0.5 秒请求刷新文件缓存。停止时同步、核验格式并补全长度，再改名。
- `<uuid>.wav`：待上传的固定内容。断网、重试和设备重启都继续使用同一个 UUID 和相同字节。
- `<uuid>.done`：播报成功后的完成标记。先从待上传文件改名，再尽力清理，避免清理失败又成为新录音。

启动恢复会按实际落盘长度修复本固件 `.part` 的 WAV 长度字段，并保留原 UUID。没有 PCM 样本的合法空录音可以清理；损坏的文件保留并阻止新录音覆盖。旧版 `pending.id` + `pending.wav` 迁移时也保留原 ID。

只能恢复已经实际落盘的完整 PCM 样本。定期 `fsync` 无法保证 SD 控制器内部缓存、突然拔卡或文件系统损坏时绝不丢数据。当前对奇数字节或未知格式采取保留并报错，避免把坏文件当作有效语音提交。

库存提交与回执一起写 SQLite。Core 已提交但客户端没收到响应时，重新发送同一录音只返回原回执；TTS 失败独立重试。

## 已执行的软件故障测试

`pnpm test` 包含 13 项测试，其中新增：

1. 直接用系统 C 编译器编译实际 `hs_outbox.c` 和原样复用的 `wav.c`，检查录音头未补全、改名前中断、已完成未清理、空录音、损坏保护、旧版迁移和多文件逐条恢复。所有文件写入系统临时目录。
2. 在真实 HTTP 连接上于库存提交后销毁 socket，确认客户端请求失败；重建 Core 和设备服务，重传同一 WAV 后库存和事件仍各一条。此测试的语音识别为显式测试夹具，不调用云端。

这些属于文件状态和软件连接故障测试，不等同于物理拔电。

## 真机验收步骤

1. 确认恢复版启动、Wi-Fi 和 Core 心跳正常，记录测试前库存。
2. 暂停 Core，使用 SET 录入“今晚两个人吃什么”，确认上传失败后文件保留。
3. 开发板断电重连，检查启动恢复的 UUID 与上传失败时一致。
4. 恢复 Core，再按 SET 重试，检查返回、扬声器播放和 outbox 清空。
5. 核对测试前后库存和库存事件数量；推荐语句不应修改库存。

## 网络恢复结果与限制

用户确认设备和电脑在相同 Wi-Fi，未启用隔离。曾出现获得 IP 后连接 Core 超时，重连后恢复；没有执行对照镜像测试，具体根因仍未确定。

修复版烧录后首次关联失败，自动管理器继续扫描和重连，约 40 秒取得 IP，随后认证心跳成功。原录音重试正常完成。这证明本次现场能够恢复，不代表已覆盖路由器重启、弱网和长时间运行等全部情形。

## 播报失败回归与自动读取

恢复的录音已使用原 ID 上传，实际转写为“今晚两个人吃什么？”，Core 返回了两人份菜单。测试前后库存和库存事件的完整数据相同。用户随后报告屏幕提示播报未完成，未听到声音，因此这一步没有按完整成功验收。

检查发现：固定 `reply.wav` 路径通过 `rename` 覆盖，当前 SDK 的 `CONFIG_FATFS_VFS_RENAME_REPLACES_DESTINATION` 未启用。修复是在临时音频完整校验后显式替换可重新下载的播报缓存。增加的 C 回归测试用包装函数模拟 FAT 的 `EEXIST` 行为，确认第二次、第三次缓存替换均成功，坏下载保留原缓存。测试总数增至 13 项。

同时增加实际 LCD 文字的串口日志和设备认证心跳上报。`pnpm hardware:status` 与 Web“真实开发板”区域读取设备实际更新时保存的屏幕文字；不是从库存提交成功推测播报成功。听感仍应与驱动播放结果区分。

修复版已以 230400 波特率烧录，bootloader、分区表和 app 均通过 esptool 摘要校验。此前 460800 写入因串口中断失败，低速完整重写后恢复；SD 与 NVS 未擦除。
