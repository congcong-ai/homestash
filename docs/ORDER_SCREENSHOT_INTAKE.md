# 订单截图解析与核对入库

更新：2026-10-23。

## 如何使用

进入“拍照入库”，将“图片内容”改为“订单截图”。建议先裁掉姓名、电话、地址和订单号，再上传清晰的 JPEG、PNG 或 WebP。点击识别后，图片会发给已配置的视觉模型；原图不写入数据库。普通物品照片、小票和 Korvo 拍照保持原流程。

系统生成待确认候选，显示平台、完整购买日期、订单/商品状态、规格和原文依据。看不清的字段保留空值或未知，不根据包装净含量推断购买件数，也不根据购买日期推算保质期。

所有订单商品默认不勾选。逐项核对实际收到的名称、类别、数量、单位、位置和日期，再勾选“我已实际收到所选商品，已核对数量”，最后确认入库。例如“一箱12盒 × 2箱”，确认2箱就只记录2箱，不自动拆成24盒。部分退款或取消的行禁止选择；整单取消或退款也由Core拒绝。状态待收货或不明时，可以在实际收到后人工确认。

刷新可以恢复候选及已提交的累计收货，但不会保留尚未提交的手动修改或实收勾选，需要重新核对。现已支持[分批收货与剩余商品续做](ORDER_PARTIAL_RECEIVING.md)：每次确认创建本次实收批次，未收齐的行保留。确认后可到库存查看和纠正。

## 数据与一致性

复用现有 `/api/intake/images` 和待确认中心，没有新建独立订单数据库或固件业务。分析请求增加可选 `kind: "order"`，省略时仍按原照片处理；订单确认必须传 `received: true`。候选、Schema、Provider、Web 与备份共享定义。

订单结构包含平台、购买日期和状态；每行增加规格与状态。Prompt明确不提取收件信息、订单号或支付信息，Schema不提供这些字段。模型自由文本仍需人工核对，上传前裁掉隐私信息更稳妥。

订单入库由 InventoryService 创建普通批次，来源为 `order`；事件保留原文依据、截图哈希关联、规格及人工实收确认。用户手动修正的数量与日期才是最终入库值。旧图片来源仍为 `camera`，旧候选和备份兼容，无历史migration修改。

完全相同图片内容在订单模式下重复上传时，复用尚未取消的候选或已确认结果；换请求ID、刷新或Core重启都不会重复生成同图订单库存。确认继续使用事务、候选归属检查、同请求回执和内容冲突校验。取消候选后允许重新识别。失败保留订单模式供原请求重试，不保存原图或服务响应。

## 当前边界

- 新版Web支持分批收货、版本冲突校验和结束剩余收货；历史已完成订单不会重新打开。详情见[分批收货说明](ORDER_PARTIAL_RECEIVING.md)。
- 去重依赖完全相同的图片内容；裁剪、重新截屏或同一订单的多张图不保证自动去重，用户仍须核对。没有按订单号跨平台合并、自动收货或自动冲销退款库存。
- 不做支付、金额、运费、优惠、SKU对账；套餐不自动拆分，不能确认数量时请手工核对。
- 图片中的状态、日期和数量可能识别错误。首次百炼测试曾把“待收货”行误标成received，收紧提示后复测正确；人工确认始终是必经步骤。单个虚构截图通过不代表真实电商截图准确率已验收。
- 默认 Mock 不伪造视觉识别；要使用真实功能需配置视觉模型。设备无需联网，本轮没有刷写固件。
