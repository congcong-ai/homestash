# 库存批次、临期与误操作纠正

## 查看与处理某一批

打开“家中库存”，每张卡片对应一个独立批次，显示批次标识、数量及单位、存放位置、购买与入库时间、包装到期日、建议食用日和开封日期。同名在库物品超过一批时会提示核对，不合并不同单位的数量。

支持搜索名称或批次前缀、按类别和位置筛选，以及提醒日期优先或最近入库优先排序。默认显示在库，另有“临期”“日期已过”“未设日期”和“已用完 / 已移出”。归零批次不会删除，可以继续查看记录和纠正。

点击“调整库存”，选择消耗、丢弃、移动或开封，核对后确认。消费与丢弃可填数量或选择全部；其他操作只显示对应字段。“编辑这一批”支持修改数量、类别、位置和日期，包括清空开封日期。

## 临期依据

Domain统一返回提醒状态、最早提醒日期、依据、剩余天数和是否估算。当前规则保持兼容：

- 包装到期日、建议食用日取最早者。
- 食品已开封时，额外比较“开封后2天”的默认估算提醒。
- 当天为需今天留意，未来1至3天为临期，早于当天为提醒日期已过。
- 没有日期会明确标为待补充，不视为长期可保存。
- 药品等其他类别不应用食品开封后2天规则。

包装到期日和建议日期的含义不同，页面显示具体依据。日期仅作提醒，不构成安全保证。当前日期日界线仍沿用Core的UTC日期；家庭时区和按品类配置开封规则尚未实现。

## 误操作如何纠正

1. 找到具体批次。误点全部消耗或丢弃后，到“已用完 / 已移出”查找。
2. 点“记录与纠正”，查看最近操作、前后状态和恢复预览。
3. 填写原因，点“确认纠正最近操作”。

纠正会恢复最近一次操作之前的完整批次快照，并新增`ITEM_CORRECTED`事件；版本继续递增，原事件不会修改或删除。误添加的批次没有之前快照，因此纠正后数量归零，保留来源与历史。

仅允许纠正该批次最近一次尚未纠正的操作。已有后续变化、版本不一致、其他批次事件或重复纠正会拒绝。纠正记录本身不能再次撤回；需要进一步调整时编辑当前批次。暂不支持任意历史操作的部分冲销或整笔多批次烹饪撤回。

采购和烹饪任务状态不会被库存纠正重新打开。对采购/烹饪产生的库存事件进行纠正时，页面会明确提示这一边界；采购入库快照仍是当时事实。

## 提交与存储

- `GET /api/items/:id/events`返回该批次完整事件，按版本倒序，不受`/api/state`最近50条摘要截断影响。
- `POST /api/items/:id/corrections`接收`{ requestId, eventId, expectedVersion, reason }`，校验批次归属、最近版本和原因。
- 原`POST /api/items/:id/actions`兼容旧请求，新增可选`requestId`和`expectedVersion`；新库存页面使用二者，阻止过时操作及网络重传重复消耗。
- 纠正的库存快照、事件和请求回执在同一SQLite事务中保存；失败回滚。跨重启同请求重放返回原结果。
- `InventoryEvent.correction`记录被纠正事件ID与原因。复用原有JSON事件/库存表，未修改历史migration。

旧客户端和设备暂未全部改为携带版本，它们仍通过原有Domain事务处理；不能把网页版本保护称为已覆盖所有设备动作。

## 验收

新增4组测试，软件测试共46项：临期依据/无日期/跨类别、同名不同单位批次隔离、消费/移动/开封/日期恢复、误添加归零、原事件不变与版本递增、跨批次/后续变化/重复纠正拒绝、动作和纠正跨重启去重、保存失败回滚、超过50条完整历史。

浏览器采用临时数据库，真实操作了临期筛选、整批消耗、归零批次查询、填写原因恢复与记录检查；模型不参与这一流程，未写日常库存或修改固件。证据见`product-evidence/inventory-batches-20261021.json`。
