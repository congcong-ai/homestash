# 食灵小院 V1.1 产品与实现要求

## 1. 已确定的产品取舍

- 全家可互动的冰箱贴，核心为食灵角色、自然相遇、共创与家庭共同回忆。
- 无真实库存概念。移除新产品入口的数量、单位、消耗、入库、出库、余量、补货、到期、新鲜度等库存流程。旧 HomeStash 后台相关能力与数据可保留，避免无关重写。
- “今天买了草莓”只触发创作角色，不声称记录了实物，也不追问数量或实物是否用完。
- 原 P2 的自动食材识别、任意程序生成、完整节气库、交易市场不进入当前路线。
- 使用现有 T5 作为当前主要开发目标。摄像头是本版核心硬件目标，目前未配。不要未经用户选择把它换成手机相机作为最终产品；手机/网页可以承担预览与回看。
- “必做 31 项”是同一体验的工程细分，不是 31 个独立子系统；完整目录见 04。

## 2. 一条完整体验

用户真实开门，角色立即醒来/挥手；达到邀请条件时用本地短音频轻轻问一句。用户不必按键或每次报身份即可接话。说“今天买了草莓”后出现草莓食灵，接着说“叫它莓老板”，角色和名称保存并反馈。合适时机邀请：“要不要和莓老板留张合影？”用户答应后进入准备/倒数，用户站稳后采集真实画面，预览可重拍、放弃或确认保存。照片、时间、食灵贴纸/主题与确认的短标题形成回忆卡。另一位家人看到同一个小院，之后能再次查看这张回忆。

设备首次不能靠开门知道是谁。用户开口后，若已有可靠的声纹身份，才自然使用称呼；未知身份照常继续。声纹或相机未就绪应有清楚状态，不让模拟值冒充真实结果。

## 3. 门事件与自然交互

- 基于实际传感器做标定、去抖、有效门事件与快速开关合并。具体角度/阈值按传感器型号、安装方向与真机日志确定，不从 IMU 名称推断有可用绝对门角度。
- 门事件到本地动画/短音频不依赖 Core 和大模型。保留物理按键发起/停止的兜底入口。
- 主动邀请每次一个短问题，无人回答即结束，不连续追问。初始可试 6—8 秒接话窗口、10 分钟主动播报冷却；它们是可配置调参起点，不是必须硬编码的产品标准。演示模式可缩短且明示。
- 同一轮聊天或拍照中重复门事件不重启流程。关门不强制截断正在说话的用户，但到收尾/无回应时及时停止本轮收音与上传。
- 设置中可关闭主动语音/开门收音，支持静默、音量和停止。明确监听状态，不以 VAD 证明声音来自当前用户或是对设备说的。
- 播报与收音做仲裁，避免听到自身声音造成循环。播报中语音打断若现成能力可用则接；否则按键停止，不从零开发 AEC 算法。

建议状态机至少覆盖休息、邀请、听取、理解/等待、播报、拍照准备/倒数、预览待选、保存中、失败。一次取消必须取消计时/回调和未生效动作，过期的云端返回不能重新启动拍照。

## 4. 语音实现与延迟

用户后续补充要求多种 TTS 配置与旧版可爱语音延迟调查，本次必须落实 `05-tts-investigation.md`。本地主机模型/HTTP 服务允许，板端中文模型移植不做；此前功能快照的笼统表述不能覆盖此新增要求。

先复用仓库 `SpeechProvider` 和当前 Core 路由，不假设 TuyaOpen 意味着正在使用涂鸦云智能体。现有 `synthesize` 返回完整 Buffer，设备下载固定 PCM WAV；不要声称已经支持动态流式播放。

- 固定招呼、收到、倒数、取消、失败提示预制成本地音频。按板卡实际文件/资源播放路径实现，断网可播。无 SD 时不能为了播报而关闭已有存储保护，必须选择可证明容量和生命周期的资源方案。
- 动态对话先保证已有语音 Provider 和新产品意图贯通、短回复；流式能力须同时验证 Provider、Core 传输、板端解码/缓冲和错误恢复。可在兼容路径上增量优化，不能只改前端开关就称低延迟完成。
- 记录：门事件、首帧、首个本地声音、用户说完、ASR 返回、意图/工具完成、TTS 首数据/播放、保存回执等时间。分开报告即时反馈与真实动态对话时延。
- 目前没有已核实的板端任意中文 TTS 引擎，不做离线模型移植。预制/缓存音频≠任意文本离线合成。
- 若真正流式接入会冲掉主流程，先交付可工作的整句路径＋本地即时反馈，明确报告流式未完成和测量值，不能用固定语音冒充 AI 动态语音。

## 5. 声纹

优先验证官方能力或当前可接入的合适 Provider：两名自愿成员先录入，实际返回可用于业务的成员标识，再接称呼/偏好。官方平台能力、当前 PID、用户侧开启、服务授权、费用和现有 Core 链路能否兼容分别确认。不要盲目新增第二套 ASR/TTS/LLM 全链路。

建议一次技术排查上限约两小时，产出明确路径/阻断；这不是开发完成估时。身份置信不足、未录入或结果过晚时使用通用称呼，继续主流程。允许纠正身份并撤回错误归属，不能默认沿用上一个人的身份。对外分享回忆不自动带上声纹样本；复用已有管理面板的录入/授权/删除能力，确需自建时范围仅限本次功能。

测试替身身份只能用于测试，界面和日志标 simulated；不能将手动下拉框作为实际声纹完成。不给人脸识别或强身份认证增加范围。

## 6. 食灵、文化与共创

管家萌小冰＋一个原创草莓食灵先做完整。角色名称、短台词可用语音或配套页修改，低风险创作直接保存并允许撤销，避免每句话都弹确认。共享小院持久化；同一事件重试不重复生成角色或奖励。

首次创建、共同命名、保存回忆形成少量可见纪念。无声纹也可以参与共养；不虚构是谁做的。不开门刷奖励，不设置饥饿、生病、死亡和缺席惩罚。

至少一条饮食/时令文化互动，使用团队已有来源或核对可靠来源；原创叙事与文化事实分开。角色、模板台词和回忆贴纸可预制；不强制做 AI 生图、复杂剧情或完整节气系统。

## 7. 摄像头、预览与回忆

### 能力接入

相机目前缺件。先核对实际板型、原厂排线定义、驱动、接口电压、引脚、屏幕/传感器共用总线、供电和可获得模组。不根据网络某块 T5 板的配置直接采购/接线。参考仓库已归档原理图和锁定 SDK；提供兼容候选与验证条件即可，不擅自下单。

T5 现有 `hs_camera_*` 是明确不支持的占位实现，需要真实新增适配；不能把 capability 置为 true 代替实现。相机缺件/未初始化时拒绝拍照并允许继续聊天。可用测试 fixture 联调服务，必须标注模拟。

### 拍照流程

- 用户主动要求拍照，或明确肯定当前有效的邀请后才拍摄。每次许可绑定当前会话/准备令牌，有过期、取消与一次使用规则；模糊/过期的“好”不触发。
- 可见拍照准备/倒数，支持取消。镜头关闭时不采集，门转动时不抓拍，先让用户站稳。
- 采集真实 JPEG，预览仅临时保存，提供重拍/放弃/确认保存；具体由主机或配套页展示，根据屏幕内存选择缩略图，不要求在小屏编辑相册。
- 无需视觉 AI。照片不进旧 `/device/v1/images/:id` 的食材候选识别流程，也不作为库存写入依据。为回忆建立隔离的设备动作/上传/回执通路。
- 时间、照片、关联食灵/互动、用户确认的标题组成回忆卡，模板贴纸可在 Web/Core 合成或叠加展示。不要虚构人物身份、关系、情绪或家庭经历。
- 确认保存后才落正式记录并播报成功；网络/磁盘失败保留可辨认状态和安全重试。同一采集/保存请求重复不多建卡片。

### 存储与回看

比赛版本优先复用现有本地 Core 做媒体文件和回忆元数据持久化；若经验证的 TF 卡路线更直接也可选，但只维护一个真值来源。明确主机无网/电脑 Core 关闭时的可用边界，不承诺完全离线全功能。

原图存仓库忽略的私有数据目录，元数据进入产品命名空间；路径不能由上传文件名任意控制。临时预览放弃/重拍后清理；正式回忆能按已有家庭/设备权限回看和删除。不要复用调试留样目录当相册，不将用户照片加入 Git 或无鉴权 public 目录。

固件/服务重启后回忆仍在；原图、卡片和删除状态一致，失败时可恢复/清理孤立文件。用可控的 staging→确认写入方式处理文件与 SQLite 事务，不能仅存在内存或 localStorage 就称持久化。

确认镜头朝向、安装高度、取景距离、两人入镜、门开合对视角的影响。硬件不到位时把这些列为明确未验收，不能拿浏览器截图替代真实机位测试。

## 8. 配套 Web 与后台保留

先检查现有路由。新版产品入口是小院、互动状态、角色改名/台词、回忆预览/回看及少量设置，设备/模拟器能走同一份业务状态。不要在原六个库存导航外再贴一个新名字而保留库存为主体验。

保留旧后台路由、API、数据库、设备管理、配置和已有认证边界。可采用新的明确产品入口或模式，给出默认入口与旧后台入口；不强制迁移全部后台 UI。现有 HomeStash 旧数据不要转成食灵库存，也不要在一次新互动中偷偷调用 InventoryService。

视觉延续成熟产品的清晰层次，柔和粉色与厨房角色气质，中文状态文案，480×320 真机逻辑画布与 390/320 手机宽度均可读。模拟器标注测试事件，角色状态、相机缺失、网络错误不得伪装实时成功。

## 9. 后做与不做

冲刺：真实声纹称呼、现成播报打断、第二种食灵/组合菜卡、设备最近回忆展示、单计时器。后台必要接通优先于扩展工具。

后做：长期个人记忆、完整相册/故事册、视觉 AI 文案、开放角色包/任务模板、完整远程账号/邀请/同步、订阅与量产运营、电池外壳定型、外部复刻资料完善。

不做：精准库存及自动扣减、余量/补货/到期/新鲜度推断、自动食材识别、常驻监控/开门抓拍、人脸库、强身份认证、惩罚性养成、任意程序生成、完整节气库与交易市场。旧后台存在相关源码不等于要求删库或全仓清除。
