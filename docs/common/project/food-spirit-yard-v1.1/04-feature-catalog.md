# 萌小冰 · 开发范围与功能筛选 V1.1

## 本次确定的变化

本轮口径覆盖旧方案中的冲突条目：**精准库存彻底删除；原 P2 整体不做；真实门事件升为核心；声纹优先验证接入；新增摄像头和家庭共同回忆主线。**旧报告保留为历史方案。这里的“必做／冲刺／后做／不做”都是建议分组，除用户明确砍掉的内容外，可在下面逐项调整。

已知：用户确认在用涂鸦 T5 AI Bot；板上已有能感知开门的角度／运动传感器；希望自然接话和声纹识人；希望拍照形成家庭回忆。摄像头目前还没配，SDK／固件版本暂不确定。尚未接触代码或真机，所有开发完成状态均为未验收。比赛暂按前文微软比赛语境整理，本次未核实最新赛制，不据此新增特定平台或评分要求。

产品口径改为：**冰箱上的食灵伙伴，在日常相遇中与家人聊天、共同创造，并把愿意留下的瞬间变成家庭回忆。**“今天买了草莓”可以触发草莓角色；角色留在小院不代表冰箱里仍有草莓。数据只保存角色、互动和回忆，不保存实物余量。不要问买了几颗、吃掉几个，也不要求用户确认实物用完。

## 比赛建议先交付什么

核心链路：真实开门 → 本地角色与短招呼 → 用户自然接话 → 召唤／命名食灵 → 邀请并确认留影 → 真机拍照 → 预览、重拍或保存 → 家庭回忆卡 → 后续回看。

**先保证这一条体验完整，再加声纹个性化。**摄像头属于用户希望本版具备的核心硬件，不能默默改成手机拍照替代。它目前未配，是当前最早需要解除的硬件依赖。声纹通路验证也应立即做；实际接入列为冲刺，能通过门槛就进入正式主线。若不通，保留通用称呼并明确说明识人尚未完成，不能把手动选人演成声纹。

建议分三步推进：第一步并行清点固件、验证门事件、确定兼容相机与到货、验证声纹权限与身份输出；第二步贯通真实对话、角色与照片保存；第三步稳定后接声纹称呼、最近回忆展示，余力才加计时器。不要同时扩建完整相册、长记忆、角色平台和商城。

本清单“必做”包含硬件、交互和必要失败处理，是同一个最小体验的拆解，不代表每项都开发一个独立子系统。无法估算工期的项没有伪造人天；先用现有代码和真机验证后再排人。

## T5 本地语音能力核查

**结论：不能据现有资料确认 T5 AI Bot 自带可用的任意中文离线 TTS。也不必让每一句声音都经过云端。**官方播放器支持本地提示音及云端 TTS 流的播放；“本地播放”不等于“本地文本合成”。见[官方音频播放器](https://www.tuyaopen.ai/zh/docs/cloud/device-ai/ai-components/ai-audio-player)。

| 声音类型 | 本次建议 | 是否等待云端 |
|---|---|---|
| 开门招呼、收到、取消、倒数、失败 | 提前录制／生成固定音频，随固件或资源包存本地 | 不需要，先验证当前固件可选播 |
| 用户自定义昵称及自由对话 | 沿用现有动态 TTS，尽早开始流式播放 | 标准链路需要云端，实测网络与首音 |
| 经常重复的动态短句 | 后续可评估首次云端生成后缓存，按文本、音色和版本失效 | 缓存命中可本地播，不是离线合成 |
| 任意新中文文本的完全离线合成 | 当前不做模型移植 | 没有现成能力证据，不作承诺 |

门事件、动画、本地招呼应独立于云端推理；设备已经能动起来，再处理用户回答。延迟要分两项：开门到本地反馈、用户说完到动态首音。后者包含收音结束判断、网络、ASR、模型、TTS 与缓冲，不应全部归因于 TTS。官方提供分片下行音频，优先利用现成流式播放，避免每次重新建立连接；连接保持与低功耗的取舍再实测。见[AI Agent API](https://docs.tuyaopen.ai/zh/docs/tuyaopen-core/agent-api)。

固件尚未知，文档接口只提供接入方向，不能直接当作你们版本可用的函数。先记录已跑通的固件版本；不为了“本地”二字临赛迁移整个 SDK。没有测量前，不承诺毫秒数或完全离线聊天。

## 门触发与声纹怎样自然配合

推荐状态：休息 → 有效门事件 → 立即角色回应 → 一句通用招呼 → 短暂接话窗口 → 用户说话 → 识别与理解 → 执行／回应 → 安静退出。已有对话时关门不立刻切断；拍照等待用户站稳，不在门转动时自动拍。

示例：“今天有什么好玩的？”用户：“我买了草莓。”设备：“让草莓精来小院住吧，想叫它什么？”用户：“莓老板。”设备保存角色名后回应。若可靠识别出已录入成员，可在这时自然使用称呼；用户未开口前不能靠门事件知道是谁。

建议初始参数：一次主动邀请只问一个问题；无回应约 6—8 秒退出接话窗口；主动语音冷却可先试 10 分钟；连续门事件合并。以上是待真机调试的起点，不是产品指标。演示模式可缩短并明示。家庭可关闭开门收音，改按键发起；VAD 只判断有人声，不会证明声音是冲着设备说的。首次说明收音状态，屏幕显示监听中，窗口结束停止这轮上传。遇厨房噪声或电视声，减少主动监听，不能靠不断追问补救。

官方平台确有声纹能力，需要平台与用户侧开启、录入并验证；声纹数据涉及云端处理／存储，官方面板有授权与删除入口，也有扩展能力费用。不能据此推断当前固件能拿到业务身份。优先用现成面板管理，两位成员先试，不建设人脸库。详见[涂鸦声纹识别](https://developer.tuya.com/cn/docs/iot/voice_print?id=Kfl8n1gfkzztq)。

声纹接入门槛：在当前 PID／固件下，确认能力可开通 → 两位成员录入 → 拿到可用于称呼／记忆的成员标识 → 交替讲话测试 → 未知／错误身份可降级。建议先限定一次不超过 2 小时的技术排查；这是投入上限建议，不是完成估时。若路径未通，主流程继续用通用称呼；保留声纹为已明确的下一项，不要求每次自报姓名。识别结果过晚不阻塞第一句回应，不把上一位说话人默认当作当前人。

## 摄像头与家庭回忆的首版

相机用于生活留影，**无需先上视觉大模型**。命名了食灵、完成了一次小任务或聊到值得纪念的事，设备可以邀请：“要不要和莓老板留一张今天的合影？”用户答应 → 画面／指示灯进入拍照准备 → 站好、倒数，可取消 → 真实拍照 → 预览 → 重拍、放弃或确认保存。

第一张回忆卡仅含照片、时间、用户可确认的短标题、食灵贴纸和关联事件。人物身份仅来自明确选择或已确认的上下文，不用图片猜测。照片边框／贴纸可以用模板合成，不需要图像生成。预览和保存放配套网页即可；主机至少播报并显示状态，不强迫在小屏上编辑相册。

**采购前先确定板型。**官方 T5AI-Board 文档列有可选 DVP 相机堆叠模块与 GC2145；这只说明该型号的路径，不证明你们称作 AI Bot 的实物同款。见[T5AI-Board 开发套件](https://docs.tuyaopen.ai/zh/docs/hardware/tuya-t5/t5-ai-board/overview-t5-ai-board)。官方 BSP 也区分有相机和不支持相机的板型，见[开源硬件资料](https://developer.tuya.com/cn/docs/iot-device-dev/tuyaos-wukong-solutions?id=Kffrlr9f755wb)。核对接口电压、排线定义、可用引脚、驱动、显示与传感器冲突后，再确定模组与到货时间，不先给一个通用摄像头型号让团队盲买。

本次存储建议选一条：若板卡有可用 TF 卡且驱动已通，先本地落盘；否则通过同局域网的电脑服务保存文件与卡片，配套页回看。后者明确属于现场原型架构，电脑服务离线时应提示保存失败，可保留临时重试而不谎报成功。Flash 不能未经容量核算直接当家庭相册。参考[官方视频输入](https://docs.tuyaopen.ai/zh/docs/cloud/device-ai/ai-components/ai-video-input)的采集接口；采集到一张 JPEG 不等于已经持久保存或能回看。

拍摄机位要实测：冰箱贴可能低于脸部，广角、距离、门角度、补光及遮挡都会影响两人留影。第一次先验证真实站位能拍到人，再投入回忆卡效果。没有配好相机前，可做标明模拟的界面联调，但不能把素材图当真机验收。若相机无法及时兼容或到货，必须显式缩减本版承诺，用户没有预先同意手机替代。

| C02 | 明确确认、倒数与取消 | 必做 | 肯定当前拍照邀请才启用采集；倒数可取消，屏幕／指示灯显示拍摄中。 | 普通聊天中的“好”不会跨会话误触；开门不自动拍照。 |

| C06 | 拍摄关闭和数据去向说明 | 必做 | 提供镜头禁用入口；临时预览放弃即释放；默认不公开、不上传照片给视觉模型。 | 关闭后不采集；跨网存储须明确说明；不对本地方案宣称远程全屋可用。 |
| C07 | 最近回忆的设备轻展示 | 冲刺 | 主机显示最近一张缩略卡／回忆入口；不做完整相册浏览。 | 显示和语音同时工作稳定；屏幕不足时改文字卡＋配套页。 |
| C08 | AI 回忆文案与看图理解 | 后做 | 用户选择后才发图做摘要／描述，先展示再确认，不猜身份、关系与心情。 | 无视觉 AI 也能完成拍照与保存；第三方发送可关闭。 |
| C09 | 月度相册、故事册和可分享纪念 | 后做 | 积累真实回忆后再做整理、导出与由用户触发的分享。 | 未选照片不外发；回忆不自动公开。 |
| C10 | 常驻监控、开门抓拍与自动公开 | 不做 | 不做连续录像、隐蔽抓拍和默认云端人脸分析。 | 所有拍摄都有当次发起／确认和可见状态。 |

角色可以一人兼任，不假定你们团队有上述人数。每阶段先保留可工作的固件与接口记录，再增量接入；比赛实际剩余时间以团队为准。

## 现场演示与验收

建议一条约 90 秒主线：真实开门、本地醒来 → 第一个人自然说话 → 生成并命名草莓角色 → 第二个人接话，若声纹已验收则用其称呼 → 邀请合影，明确答应 → 倒数拍照、预览并保存 → 配套页展示回忆卡 → 再次进入仍能回看。相机关闭、拒绝拍照和未识别用户的分支都应走得通。

开门事件至少覆盖正常、慢开、连续开关与轻碰；语音覆盖无回应、噪声、取消、断网和播放仲裁；声纹若纳入则两人交替与第三位未知用户都留日志；相机覆盖未同意、倒数取消、重拍、放弃、存储失败与重试；回忆覆盖重启、回看、删除；重复保存只生成一张卡。建议核心链路连续跑 5 次并记录，达不到就继续修复。这是赛前检查建议，当前并未执行真机验收。

开发前实际需要确认：板卡丝印／BSP、当前 SDK／固件、传感器型号、摄像头兼容与到货、是否能导出声纹成员标识、现成音频入口，以及最终采用 TF 卡还是局域网存储。用户目前无法确认 SDK，因此这些属于工程排查项，不能当成用户尚未批准功能。

## 这一轮明确不建设的内容

精准库存的数据库、入库／出库／盘点界面、余量／补货／临期推断全部删除。原 P2 的自动食材识别、任意程序生成、完整节气库和交易市场整体移出，不作为赛后必做。拍照不扩展成家用监控或人脸识别。保持角色与照片的情感价值，不把设备做成家庭日常数据填报工具。

商业上仍可讲成品硬件、原创外观与角色、可选 AI 服务的方向，但订阅支付、商城、完整远程账号与设备运营留到稳定试用之后。比赛材料另准备功能完成表、关键架构、原创与文化来源、真实演示视频和已知限制；不把市场需求、付费和销量写成已验证。
