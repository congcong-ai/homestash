# 语音延迟调查与可配置 TTS 重构要求

## 用户新增要求

用户反馈旧版“萌化”语音响应很慢，要求查清原因，并支持多种 TTS 配置：可以用本地生成，也可以调用云端 API；如果本地可加快也应评估。此要求纳入本轮大版本重构，不能只写成赛后事项。

这里必须区分三种位置：T5 板端合成、电脑/家庭主机上运行本地模型、外部云端合成。它们都不同于“本地播放预生成音频”。用户允许本地主机合成；之前不做板端中文模型移植的决定仍有效。

## 当前代码里已经确认的事实

1. `packages/ai/src/speech.ts` 的 `BailianSpeechProvider.synthesize()` 调用百炼 `/api/v1/services/aigc/multimodal-generation/generation`，返回音频 URL，然后完整 fetch 结果，最后 `normalizeAudio()`。因此当前已查到的动态 TTS 实现是**云端模型合成**，不是本地神经网络推理。
2. `speechFromEnv()` 的默认 TTS model 为 `qwen3-tts-flash`，默认 voice 为 `Momo`，可通过环境配置覆盖。仓库没有当前运行环境的完整证据，不能说正在运行的进程必然使用默认值。只读输出 provider/model/voice/endpoint 的脱敏配置，不输出 Key。
3. `normalizeAudio()` 创建临时文件并启动 ffmpeg，转为 16 kHz/mono/16-bit PCM WAV。当前参数是采样格式转换，没有 pitch、变调、可爱变声滤镜，也未见本地 TTS 模型加载。
4. `services/kitchen-core/src/device-reply.ts` 的 `deviceReply()` 用规则缩短、组织文字并加“好哒”等语气词；注释明确不调用模型重写业务事实。`packages/ai/src/index.ts` 的 persona 是模型提示词与前缀，不是二次音频合成。当前查到的设备回复路径没有“先普通 TTS，再可爱 TTS/变声”的二次合成步骤。
5. `POST /device/v1/captures/:id` 当前等待完整上传、ASR、结构化业务解析（真实模型或 mock 由配置决定）及提交后才返回文本回执。烹饪生成/问答分支还可能有额外模型调用，但不应误称统一存在一次“萌化润色”。
6. `/device/v1/captures/:id/audio` 是收到设备后续 GET 才开始查缓存/合成；完整音频下载、转换、写缓存结束后返回 Buffer。它没有把云端首片即时透传给设备。
7. T5 `hs_transport_reply()` 先取得完整 HTTP body、写文件并替换缓存；`hs_audio_play()` 再读取 PCM 播放。单独让云端 API 返回流并不能自动改善这里的完整等待。
8. 当前音频缓存以设备/采集 ID、model/voice 等组成，主要复用同一录音重试；不同请求说相同短句并不直接共享此缓存。重构若改为内容缓存，需要完整的配置维度和请求隔离。

**静态结论：当前工作树不支持“本地合成导致慢”或“先普通音频再萌化导致慢”的猜测。已确认多个串行完整等待点，尚未测量它们各自耗时。**远程部署/历史固件与此工作树是否一致未核实，不可把代码结论当成线上实测原因。

## 先建立测量，再说瓶颈

新增可重复、脱敏的测量入口/日志，用同一 correlation/request ID 串联：

- 录音结束判断与等待、上传时长。
- ASR 请求/返回。
- 意图解析、额外问答/菜谱等模型调用、业务提交。
- 回复文字整理（直接规则/本轮回复生成），不要凭感觉归因。
- TTS 请求到响应/首数据、URL 音频下载。
- ffmpeg 进程与格式转换、缓存读写。
- Core 音频响应、设备接收开始/结束、板端首帧播放和播放结束。

记录冷/热、缓存命中/未命中、句长、音色/速度/采样格式、网络、Provider 和真实/模拟状态。服务端可用单调时钟计算自身耗时；跨设备时钟未同步时不可直接相减，设备首音要由设备单调日志或可审阅录音测量。区分首字节、首个可播放音频片、设备首音和全段完成，不用任何一个代替另一个。

可测 3 类短句（应答、命名反馈、拍照邀请），相同条件重复采样并报告样本数、首音/完整时长和分布；样本少就给逐条结果，不编造统计稳定性。需要云端配置缺失时先实现探针和测试，再准确说明真实测量缺口，不盲目长循环产生调用费。

## 本次必须支持的配置与边界

将 ASR 和 TTS 的选择拆开，保留现有环境配置兼容。TTS 至少明确区分：

- **本地固定音频**：门招呼、倒数、取消、状态提示的即时播放。
- **现有百炼云端 TTS**：保留可用实现，可配置 model/voice、服务端支持的速度/风格等参数；不向不支持的 API 硬塞参数。
- **本地主机 TTS 服务适配**：可配置 `local-http` endpoint、协议类型、超时、音色/模型、输出格式与凭据引用，通过实际协议的适配器接入。可以先支持一个文档明确的兼容 HTTP 合成契约，配真实本地测试服务验证，不把“通用 HTTP”包装成支持所有 TTS 引擎。未指定可用本地引擎时不擅自下载大型模型，不把 adapter 测试当成本地模型已跑通。

如果已有合适的直出可爱音色，优先直接选择，不为了可爱额外串联第二个大模型或语音转换模型。可选后处理必须可关闭、分别计时并展示额外成本；这次不要求开发可爱变声算法。

配置可由服务端环境和最小配置页面管理，前端只见非敏感状态；Key 保持服务器端。设置真实生效、可试听和恢复默认。未配置/不支持/服务未连接与已验证状态区分。切换配置不清空家庭业务或触发旧库存操作。

默认不未经说明把本地失败音频发到另一个外部服务；回退策略可配置并显示当前采用的 Provider。合成失败可用本地短提示/屏幕说明，不重新执行业务。

## 优化优先次序

1. 本地固定反馈、缩短回复、避免无必要二次调用；不改变业务真实性。
2. 尽早开始合成已确定的回应内容。成功类语音必须等真实工具成功才播报，不能用推测中的成功文本掩盖等待。
3. 检查是否能直接要求下游输出板端支持的格式，减少结果 URL 下载或 ffmpeg；不能仅根据模型名假定 API 支持。保留已验证兼容路径。
4. 对常用固定句或完全相同动态句做有界内容缓存。key 至少包含 Provider/endpoint 标识、model/version、voice、text、speed/style、输出格式与转换版本；凭据值不进入文件名/日志。防止切音色还放旧缓存、不同家庭私密内容串读，并发不重复合成，取消不播放过期内容。
5. 有明确 Provider 和板端支持证据后实现端到端流式/分句低首音：Core 及时转发，板端可边收边播，有缓冲/背压/取消/失败和内存上限。固定 WAV 头与整段校验的旧契约不能当流式协议盲用。新旧能力协商，旧板路径保留。
6. 本地主机模型是否更快以同文案/相同机型/预热/并发条件测量；需要区分模型冷启动与稳态。不要承诺“云端一定更快”或“本地一定低延迟”。

## 验收

- 能说明实测主要瓶颈，或明确缺测阶段与原因，不能只给“网络慢”推测。
- 云端与 local-http 配置、响应校验、错误/取消/超时、缓存隔离均有测试，ASR 可保持原 Provider。
- local-http 至少有实际本地 HTTP fixture 契约验证，真实模型是否配置单独记录；没有的状态不可显示已连接。
- 核心交互使用本地固定提示，不因云端离线失去即时角色反馈；不能把它的速度当动态 TTS 首音。
- 比较优化前后的同条件样本，不以模拟服务耗时代替真实云或本地模型时延。
- 若端到端流式因既有协议/硬件限制本轮未完成，准确标记限制并交付已完成的配置、测量和实际有效优化，不称全链流式已实现。
