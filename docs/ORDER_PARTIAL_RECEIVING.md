# 订单分批收货与剩余商品续做

更新：2026-10-23。

## 操作流程

1. 在“拍照入库 → 订单截图”识别后，勾选实际收到的商品，核对订单总量和计数单位。
2. 填写本次实收数量，而非再次填写整单总量。例如订单2箱，今天只收到1箱，本次填写1箱。
3. 明确勾选实收确认，再确认入库。系统创建本次独立批次，累计已收1箱、剩余1箱，订单继续留在待确认中心。
4. 以后从待确认中心继续核对，或重新上传同一图片。剩余数量与累计收货会恢复，不需要再次识别。每次实收都须重新勾选确认。
5. 收齐所有可收商品后自动完成。退款/取消行不进入待收货额度；无法确认总量的行仍需人工核对。
6. 如果剩余商品不再接收，点“结束剩余收货”，核对说明后再次确认。已入库批次保留，不撤销库存，不进行退款冲销。

可以校正模型给出的订单总量，但不能低于已经收到的数量，也不能让本次实收超过剩余数量。某行已经收齐或结束后不再开放新增；误收可到库存事件中纠正，确有额外采购请建立新批次。

同一商品已有收货后计数单位锁定，不自动把箱、盒、克相互换算。数量最多六位小数，使用固定精度累计，避免0.1与0.2留下剩余尾差。规格仍只作核对依据。

## 状态与数据

图片候选增加可选 `fulfillment`，包含收货版本和每行总量、原单位、累计已收与结束标记。没有新增表，也没有修改历史migration。照片、小票、原有订单候选保持兼容；历史已完成订单不会重新打开。

新Web确认请求携带 `expectedRevision`，每行传订单总量，物品数量表示本次实收。Core在一次事务中校验剩余额度、创建批次、累计收货并更新回执。旧版本页面或双窗口使用过时版本会被拒绝；同一请求网络重试返回原结果。启用分批后的记录不允许绕过版本号用旧接口重复确认。

旧客户端对尚未启用分批的旧候选仍可按原协议一次确认；新版Web始终使用分批协议。开始分批后，所有后续收货与结束动作必须使用新版本校验。

入库批次快照累计保存在原图片记录中；库存之后消耗、丢弃或纠正不会反向增加订单剩余额度。需要修正库存时仍走InventoryService与事件记录。分批收货失败时，库存、事件、累计进度和请求回执一起回滚。

`finish-order` 入口要求登录、来源校验、请求ID、当前版本和明确的结束确认。已有收货的结束订单保持已完成状态，同图重新上传返回原结果，不重新开始入库。没有任何收货时结束为取消，允许之后重新识别。

备份包含收货进度，恢复前校验候选引用、累计数量、计数单位和批次快照；不能把已有收货记录篡改为可重新识别的取消状态。旧备份没有进度字段时保持原行为。
