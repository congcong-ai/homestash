## 可复验命令

先运行 `pnpm dev`，它会释放3000/3100/3101端口再启动。运行以下检查不会修改日常库存：

```sh
pnpm lint
pnpm typecheck
pnpm test
pnpm build
python3 scripts/hardware/check-wifi-profiles.py
python3 scripts/hardware/check-power.py
pnpm hardware:build:generic
pnpm hardware:acceptance 300
```

`hardware:acceptance`只读Core和SQLite，默认观察300秒；允许60至3600秒，输出到系统临时目录。它检查心跳年龄、意外重启、库存/事件完整摘要，并记录内部堆内存和OTA状态。观察期间请勿主动重启、升级或修改库存，否则报告会如实失败。

真实百炼探针使用临时数据库，会产生模型调用量：

```sh
pnpm exec tsx scripts/hardware/probe-inventory.ts
pnpm exec tsx scripts/hardware/probe-recipes.ts
pnpm exec tsx scripts/hardware/probe-cooking.ts
```

烹饪播报只对同一采集ID最多重试三次503，不重做库存动作；报告保留每次状态。回答断言允许自然语序，并接受库存不足时拒绝扣减，不能通过强制模型固定措辞掩盖业务问题。

串口监听用本项目独立配置中的USB序列号匹配开发板，不默认打开任意串口。六页验证可与同一个监控进程共用命令队列：

```sh
python scripts/hardware/monitor.py --seconds 900 --status --command-file /tmp/homestash-device-commands.txt
pnpm exec tsx scripts/hardware/probe-pages.ts /tmp/homestash-device-commands.txt
```

命令队列须先建立为空文件并设置权限600。不要运行第二个串口进程争抢端口。串口`@reset`由监控工具执行一次UART复位，仅供验收；配置参数不回显。`sleep-light`和`sleep-deep`用于3秒定时实验，仅空闲、启动确认完成、无待处理录音/照片时接受。它们不是自动节电策略，也不承诺SET或触摸可以从深睡眠唤醒。

## 固件边界与复用

原SmartBadge继续独立存在。本轮不修改其源码、配置或SDK。来源与摘要见 `FIRMWARE_IMPORT_MANIFEST.json`；原始来源摘要和HomeStash修改后摘要分别保留。

直接复用：Korvo BSP、ES8389/I2S、LCD/GT1151触摸、ADC按键、SD、LED、Camera底层组件，以及WAV和增益算法。GPIO唯一依据为已导入BSP的 `vendor/espressif/esp32-s31-korvo/components/esp32_s31_korvo/include/bsp/esp32_s31_korvo.h` 和审计，不根据网页猜引脚。

抽离复用：Wi-Fi扫描/连接/保存、录音文件恢复、队列、HTTP与构建诊断经验。新增的是HomeStash设备协议、库存幂等、FreshMate页面、图片审核、NVS配置、OTA和受控休眠。工牌员工归属、后台API、COS授权、业务状态机、提示词及UI没有进入HomeStash Domain。

当前LCD手动配网基于已验证的Wi-Fi管理器，按路线“优先复用稳定现有配网方案”推进。BLE配网作为后续产品能力单独列出；BLE诊断通过不能将其标记完成。

## 产品结论与后续硬件输入

- 已证明按键说话、库存与菜谱、免手陪做饭、LCD/Web同步可以在现有Korvo实现，无需购买另一块ESP32。
- 产品仍依赖用户记得录入/消耗，模型数量、单位、临期建议需核对；图片必须人工确认，不能自动加库存。
- 现有LCD足以支撑PoC，当前不需要E-Ink。最终屏幕类型要根据日常可读性、交互、成本和功耗实测决定，尚未得出E-Ink必须保留的结论。
- Camera可拍可上传，但当前真实桌面照片并未识别出食材，不足以证明其产品收益；保持可选，Voice/Web闭环不依赖Camera。
- 未来Rev.A应优先保留按键、麦克风、音频输出、可选显示、Wi-Fi、配置恢复、调试/恢复接口，并为相机/显示/音频预留按需电源控制。此处只是能力输入，没有设计或冻结PCB。
- 工牌业务、USB-A主机、RGB灯、大尺寸LCD、SD和Camera是否保留，应按SKU和真实使用取舍，不能仅因Korvo已有就全部带入消费版。当前SD承担离线恢复，移除前必须有替代存储方案。
- 开发版SDK、间歇性局域网不可达、供电/USB中断、未知字形及云端语音可用性仍是主要风险。连续连接失败的有限重连不是已确定并修复网络根因。

## 本轮证据与最终结论

本轮结果统一记录于 `hardware-evidence/phase1-acceptance-20261020.json`；原始日志、录音、恢复镜像与私密配置仅保存在本机忽略目录或临时目录。未通过或未测项目不会用Mock、历史结果或截图替代。

### 休眠首轮故障及隔离

0.3.3执行Light Sleep时触发CPU0中断看门狗，设备自动重启。使用同一构建ELF解码后，调用栈包含SDK的 `esp_psram_impl_resume_from_halfsleep_mode`，不能将本次Light Sleep判为通过。Deep Sleep定时唤醒已记录 `wakeup_cause=4` 并重新联网。

0.3.4仅在HomeStash自己的配置中关闭 `CONFIG_PM_SLP_SPIRAM_HALFSLEEP_ENABLED`，保留PSRAM供电，避免进入已观察到故障的半睡恢复路径。没有关闭看门狗，也没有修改共享SDK或SmartBadge。关闭该节电选项的代价是不能据此宣称获得最佳睡眠电流；最终是否通过以0.3.4真机日志为准。


0.3.4关闭PSRAM半睡后，Light Sleep仍产生RGB LCD underrun中断风暴及IWDT。这个结果也判为失败，不能称为已修复。0.3.5增加正确的显示生命周期：先调用现有 `esp_lv_adapter_sleep_prepare` 暂停LVGL并分离面板，再释放LCD panel/DMA；醒来复用原 `bsp_display_new` 建面板并 `esp_lv_adapter_sleep_recover`，保留页面对象与触摸输入。BSP仅新增释放缓存接口，没有修改引脚或重写驱动。最终结果另行记录。


0.3.5首次真实Light Sleep返回 `ESP_OK`、`wakeup_cause=4`，随后面板重建与网络恢复返回成功，没有复现该次underrun/IWDT。设备报告的 `esp_timer` 差值为5,051,168微秒（命令设置3秒）；该值只作为设备计时记录，不当成校准的墙钟睡眠时间或电流测量。Deep Sleep也记录到定时唤醒原因4，并重新拿到IP和认证心跳。后续实体屏幕、语音与连续运行结果见结构化证据。


## 本轮结论

自动集中验收通过：32项软件测试、lint/typecheck/Web构建、固件构建、Wi-Fi与电源真实C代码主机检查、六页实际设备文本比对、Core短时中断、OTA待确认启动复位回滚，以及0.3.5的Light/Deep Sleep和唤醒恢复。0.3.5已安装于ota_1，启动标记valid。

0.3.5完成300,381毫秒连续观察，60次采样，无超时心跳或意外重启，内部空闲堆首末及最小/最大均63,131字节。观察及整个本轮的库存与事件完整数据保持4项/4条不变。该结果只覆盖5分钟短时运行，不推导多天或所有网络环境稳定性。

**本轮Phase1核心Korvo PoC验收通过（有保留项）**。用户已补充确认唤醒后实际LCD与“家里有什么”播报正常，也实际执行了下载提示后的断电、约3秒后重连。实测随后运行0.3.5/ota_0/valid并回首页；原槽为ota_1，更新可能已完成才断电，所以不能据此确认精确写入中途的掉电保护。

为区分阶段，随后启动受控慢速下载。窗口内未检测到新的物理断电，结束受控服务时最后记录传输1,933,312字节（完整镜像2,216,720字节），设备明确拒绝未完成镜像并保留ota_0。该项记录为网络中断，不能冒充物理中途断电。

最后已恢复正常Core并完整重试同一0.3.5应用，设备由ota_0切到ota_1，重启、30秒启动自检及valid确认通过，认证心跳和首页正常；库存和事件完整数据仍保持4项/4条。临时下载服务已关闭，当前无需继续拔电。更新页是临时UI，重启回首页是预期行为，不代表恢复失败。

首次断电的阶段不确定；后续受控复测已补齐下载中途物理断电恢复证据，见下节。未覆盖Flash全部指令或启动元数据提交瞬间，也不代表整个路线已100%完成。

BLE产品配网、复杂弱网/多天压力及真实电流测量单独保留；当前没有购买额外开发板或E-Ink、没有修改SmartBadge，也没有进入微信或PCB阶段。原始失败记录与后续通过记录均保留，不能删除失败历史后宣称首次通过。

### 后续受控中途断电复测

用户重新执行全部断电约3秒后接回UART。本次慢速传输在262,144 / 2,216,720字节中断，下载期间UART断开，Core随后重新收到启动后心跳；仍运行原ota_1 / 0.3.5 / valid，首页及联网恢复。此项取得了下载中途断电保留原应用的证据，取代此前“该阶段未覆盖”的结论；不代表覆盖Flash全部指令及启动元数据提交瞬间的故障时序。

收尾已完成：用户通过LCD恢复正常Core（3101）并确认安装，自动重启回首页。最终实测0.3.5 / ota_0 / valid；关闭3102临时代理后仍收到新心跳，确认直连正常Core恢复。库存仍为4项、4条事件。临时代理及串口监控已停止，私密命令队列已清空，无需继续拔电。
